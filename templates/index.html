Insecure Deserialization Lesson

Overview

This lesson will examine insecure deserialization.

This lesson will teach learners:

  • Serialization, insecure deserialization, and the security risks it poses
  • How to identify, exploit, and patch insecure deserialization
  • How to serialize JSON data

Learners will submit comments on a forum, then edit serialized comment data to introduce their own malicious objects. The lesson will explain how serialization works, how insecure deserialization occurs, how to exploit it, and how to mitigate it.

The application features a website with an HTML frontend and a backend made using Flask. Comments will be serialized using pickle and then stored in a cookie. When the page is reloaded, they are deserialized and loaded onto the page.

Vulnerability

Serialization is the process of converting data (often an object) to a format that is easier to store or transfer. It often means turning something into a string of bytes or text, then saving that to a file or sending it over a network. When the data is needed again, it is deserialized back into its original state.

This can be dangerous, however. If the user has control over what information is deserialized, they can alter the information to contain their own serialized object instead. When that object is deserialized, it can perform arbitrary code (such as os.system("rm -rf")).

Exploit

When looking for potential exploits, it's important to check cookies and local storage to see if they contain any useful information.

To check cookies, press Ctrl + Shift + I on Windows/Linux or Cmd + Option + I on Mac. Navigate to Storage on Firefox or Application on other browsers. Finally, click on the web address under Cookies.

Try leaving a comment in the sandbox. A new cookie should pop up with the name comments. The value consists of seemingly random characters, most of which are letters, implying that it may be base 64 encoded. Test this by copying the information and pasting it into this base 64 decoder. You should see legible words, including some comment information, suggesting that the comments are stored as base 64 encoded data in the cookies and loaded when you reload the page. To confirm this, try reloading the page, and see if your comment stays. If it does, then try deleting that cookie entry and reloading again. The new comment should go away.

Patch

The vulnerability stems from the inherent danger in deserializing user-controlled information. To patch it, we have two options:

  • Don't store the serialized comments in a place where users can alter them
  • Don't serialize and deserialize them as potentially dangerous objects
For this lesson, we will choose the second option. Instead of serializing the comments as objects using pickle, we will serialize them as a JSON list. JSON cannot encode arbitrary objects, which is what makes pickle dangerous.
