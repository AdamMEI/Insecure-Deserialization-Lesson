Persistent Cross-Site Scripting (XSS)

Overview

This lesson will examine persistent cross-site scripting, also known as XSS.

This lesson will teach learners:

  • The difference between persistent and non-persistent cross-site scripting
  • How to identify code that is vulnerable to persistent cross-site scripting
  • How to exploit code vulnerable to persistent cross-site scripting
  • How to patch the innerHTML persistent cross-site scripting vulnerabilty

This lesson will explain the different types of XSS vulnerabilities, how they are exploited, and the impact that they have. It will guide the learner through exploiting a comment submission system on a public forum. Finally, it will instruct the learner on how to fix an XSS vulnerability.

The application is a simple forum for a TV show, which features a comment section where users can submit their thoughts on the show. The unsanitized inputs are saved and displayed for the user by editing the innerHTML property.

Vulnerability

XSS is a vulnerability found in web applications. Attackers inject code into pages, which can then execute a wide variety of dangerous actions. This often occurs when the attacker submits some information that is meant to be read as text, but it is instead interpreted as a form of data like HTML.

Non-persistent, or reflected XSS, usually occurs through an HTTP request. It is often delivered via a URL in an email, tweet, or similar medium, and it comprimises the user who follows that URL.

Persistent XSS (as seen in this example) is less common and more dangerous. The attacker stores their code in the page, and anyone who views the page then executes the code. Because there can be many more victims, and they do not need to make a mistake such as following a malicious URL, persistent XSS attacks can be devastating.

Exploit

In the sandbox on the right, users can submit comments about a TV show. Try submitting a comment and see what happens.

Next, try submitting the comment with some tags, like <h1>comment</h1>. You should see your comment become a heading. This is likely unintended, so you're already exploiting a bug. However, you can do something much more damaging.

If you've worked with HTML before, you might know where this is going. Try typing <script>alert('XSS Exploit!')</script>. And... most likely, nothing will happen. This is because most browsers filter out <script> tags used this way.

There are a few ways to get around this, however. One of the most common goes something like: <img src="x" onerror="alert('XSS Exploit!')">. The browser will try to load the image, but because x is an invalid source, it will run the onerror code. If you refresh, it will continue to display this alert each time.

Patch

Select Editor in the top right. This is the HTML, CSS, and JavaScript that handles the sandbox website.

Scroll down to the addComments function. This is where the vulnerability occurs. div.innerHTML = comment interprets the comment as HTML, not just plain text. To fix this, simply replace innerHTML with textContent.

innerHTML is not the only way for an XSS vulnerability to occur, but it is one of the most common methods. Whenever using user-provided input, ensure that it is interpreted as plain text or properly sanitized to avoid cross-site scripting.
